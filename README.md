## 📌 Проработка шагов

### Шаг 1: Отчет по интеграции и тестированию аллокатора
#### Введение
В рамках данной работы был проведен эксперимент по интеграции и тестированию специализированного аллокатора памяти. Аллокатор был взят из открытого репозитория [Allocator](https://github.com/endurodave/Allocator). Целью эксперимента являлось сравнение производительности различных стратегий выделения памяти при работе с большим объемом данных.

#### Теоретическая часть
#### Что такое аллокатор памяти?
Аллокатор памяти — это механизм, управляющий выделением и освобождением памяти в программе. Стандартный аллокатор (операторы `new`/`delete` или `malloc`/`free`) работает с кучей (heap) операционной системы, что может быть медленным из-за:
- Поиска подходящего блока памяти
- Фрагментации памяти
- Накладных расходов на служебную информацию

#### Типы аллокаторов в эксперименте
| Тип аллокатора | Описание | Преимущества | Недостатки |
|----------------|----------|--------------|------------|
| **Heap** | Стандартное выделение памяти через `new[]`/`delete[]` | Универсальность | Высокие накладные расходы |
| **Static Pool** | Фиксированный пул памяти (статический массив) | Очень быстрое выделение | Ограниченный размер |
| **Heap Blocks** | Аллокатор с фиксированным размером блока | Быстрота + гибкость | Может расходовать больше памяти |

#### Как работает пул памяти?
Пул памяти предварительно выделяет большой блок памяти и разбивает его на блоки фиксированного размера. Свободные блоки хранятся в связном списке (free-list). Выделение памяти — это просто извлечение первого блока из списка (O(1)). Освобождение — добавление обратно в список. Например: [Свободный список] -> [Блок1] -> [Блок2] -> [Блок3] -> NULL (Блок 1 = Выделен, остальные свободные).

#### Экспериментальная часть
#### Конфигурация эксперимента
Параметры тестирования из кода:
- static const int MAX_BLOCKS = 10000;      // 10,000 операций
- static const int MAX_BLOCK_SIZE = 4096;   // 4 КБ на блок
Тест выполнял следующие операции:
1. Выделение 10,000 блоков по 2 КБ
2. Освобождение каждого второго блока
3. Выделение 10,000 блоков по 4 КБ
4. Освобождение оставшихся блоков
5. Освобождение всех блоков

#### Анализ результатов
#### Почему Heap показывает стабильно высокое время?
1. **Поиск свободных блоков**: При каждом `new[]` аллокатор кучи должен найти подходящий непрерывный участок памяти
2. **Фрагментация**: После множества выделений и освобождений память становится фрагментированной
3. **Системные вызовы**: Операционная система участвует в управлении памятью

#### Почему Static Pool и Heap Blocks в 15-20 раз быстрее во 2-м и 3-м запусках?
| Фактор | Объяснение |
|--------|------------|
| **O(1) сложность** | Выделение — просто извлечение из списка |
| **Отсутствие фрагментации** | Все блоки одинакового размера |
| **Локальность данных** | Блоки находятся рядом в памяти |
| **Кэш процессора** | После первого запуска данные в L1/L2 кэше |

#### Аномалия: первый запуск Static Pool медленный
В первом запуске Static Pool показал время, сопоставимое с Heap (35,363 vs 41,466 мкс). Причина:
1. **Инициализация пула**: В первом запуске происходило заполнение свободного списка
2. **Промахи кэша**: Данные пула еще не попали в кэш процессора
3. **Виртуальная память**: Требовалось отображение физических страниц

#### Почему у Heap Blocks большой первый выделение (22,932 мкс)?
В режиме `HEAP_BLOCKS` аллокатор при первом выделении создает новый блок через `new[]`, что вызывает системный вызов. В последующих запусках блоки переиспользуются через free-list.

#### Выводы
1. **Пул-аллокаторы эффективнее** стандартной кучи в 15-20 раз при многократном использовании
2. **Первый запуск прогревочный** — результаты первого запуска следует исключать из анализа, так как они не отражают установившийся режим работы
3. **Heap Blocks оптимален** для общего случая — сочетает скорость пула с гибкостью динамического выделения
4. **Static Pool идеален для встраиваемых систем** — предсказуемое время выполнения и отсутствие динамических выделений после инициализации
5. **Важность локальности данных** — кэш процессора критически влияет на производительность аллокаторов

#### Заключение
Интеграция специализированного аллокатора в проект может дать значительный прирост производительности при работе с большими объемами данных. Наибольший эффект достигается при многократном выделении/освобождении блоков одного размера. Рекомендуется использовать `Allocator` с пулом памяти для высоконагруженных компонентов системы.

#### 3. Что было сделано
#### 3.1. Интеграция Allocator
Аллокатор был интегрирован в проект как опциональный компонент, управляемый макросом `USE_ALLOCATOR`.

#### Файлы, добавленные в проект (из репозитория endurodave/Allocator):

#### Изменения в существующих классах:
В каждый из классов, где требуется контроль над выделением памяти, добавлен макрос `DECLARE_ALLOCATOR` в заголовочном файле:
- #ifdef USE_ALLOCATOR
- DECLARE_ALLOCATOR
- #endif

А в соответствующем `.cpp`-файле – макрос `IMPLEMENT_ALLOCATOR`:
- #ifdef USE_ALLOCATOR
- IMPLEMENT_ALLOCATOR(ClassName, 0, nullptr)
- #endif

#### Где применялось:
- BBV
- X (вспомогательный класс для доступа к биту)
- BoolInterval
- BoolEquation

**Настройка сборки (файл laba_SAT1.pro):**

#### Режим работы аллокатора:
- Параметры `objects=0`, `memory=nullptr`, включают режим `HEAP_BLOCKS`.
- Каждый объект выделяется отдельным блоком через new `CHAR[m_blockSize]`.
- При освобождении блоки возвращаются в свободный список, а не сразу в кучу.

#### 3.2. Паттерн «Стратегия» (Strategy) для выбора переменной ветвления
#### Проблема:
В исходном коде метод BoolEquation::ChooseColForBranching() жёстко реализовывал одну эвристику выбора переменной.

#### Решение:
Выделен интерфейс стратегии и две реализации.

#### Логика стратегий (файл `PatternStrategy.cpp`):
- `MinDefendedStrategy` – оригинальная эвристика: выбирает переменную с **наименьшим** числом определённых значений (или с наибольшим числом -).
- `MaxOccurrenceStrategy` – новая эвристика: выбирает переменную с **наибольшей частотой** вхождения в активные дизъюнкты.

#### Интеграция в `BoolEquation`:
- class BoolEquation {
-     // ...
-     PatternStrategy* strategy;
- public:
-     void setStrategy(PatternStrategy* s) { strategy = s; }
-     int ChooseColForBranching();
- };

#### Метод `ChooseColForBranching()` теперь делегирует вызов стратегии (если она установлена).
#### Использование в `main.cpp`:
- При запуске программа предлагает пользователю выбрать стратегию (1 или 2).
- Создаётся объект выбранной стратегии.
- Передаётся в объект `BoolEquation` через `setStrategy()`.

#### 5. Анализ результатов
#### 5.1. Работа Allocator
#### Как подтверждается корректная интеграция:
1. Код компилируется и выполняется при `USE_ALLOCATOR=1`.
2. При использовании аллокатора:
  - В `Allocator::Allocate()` добавляются счётчики (`m_allocations`, `m_blocksInUse`, `m_blockCnt`).
  - Если бы аллокатор не работал, программа либо падала бы (из-за неправильного `new`), либо выдавала бы совершенно другой результат (при повреждении памяти).
  - **Результат корня совпадает с оригинальным**, что доказывает: аллокатор не нарушает логику работы решателя.
3. **Режим** `HEAP_BLOCKS` (objects=0) означает, что каждый объект получает отдельный блок памяти через `new CHAR[m_blockSize]`, а при удалении возвращается в пул, но не сразу в кучу. Это работает прозрачно для остального кода.

#### 5.2. Работа паттерна «Стратегия»
#### Почему корень одинаков для обеих стратегий?
Это **нормальное поведение** для данной конкретной формулы, и вот почему:
- Задача SAT может иметь **несколько решений** (или одно).
- DPLL – **полный** и **корректный** алгоритм: он найдёт решение, если оно существует, независимо от выбора переменной.
- Разные стратегии влияют на порядок перебора (размер дерева поиска, скорость), **но не на факт существования решения** и **не на само решение**, если формула выполнима.
- В данном примере (`Sat_ex13_3.pla`) **все стратегии привели к одному и тому же корню**, что говорит о:
  - Уникальности решения или
  - Том, что порядок ветвления не изменил найденный лист.

#### Что изменилось бы при других условиях:
- Время выполнения.
- Глубина дерева поиска.
- Возможно, другой корень (если решений несколько) – но для формулы из примера решение единственное.

#### 5.3. Теоретическое обоснование паттерна «Стратегия»
#### Определение:
**Стратегия** (Strategy) – поведенческий паттерн проектирования, который определяет семейство алгоритмов, инкапсулирует каждый из них и делает их взаимозаменяемыми. Стратегия позволяет изменять алгоритм независимо от клиентов, которые его используют.

#### Применение в проекте:
- Алгоритм – выбор переменной для ветвления.
- Клиент – класс `BoolEquation` (или `main.cpp`).
- Семейство алгоритмов:
  - `MinDefendedStrategy`
  - `MaxOccurrenceStrategy`

#### Преимущества в контексте SAT:
- **Гибкость:** легко добавить новую эвристику (например, `VSIDS`, `Jeroslow-Wang`), не меняя основной алгоритм.
- **Тестируемость:** можно сравнивать стратегии на одном наборе формул.
- **Расширяемость:** стратегии могут использовать дополнительную статистику из решателя.
